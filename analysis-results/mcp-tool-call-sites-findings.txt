2. Session connection and retry
-------------------------------

src/services/mcp/client.ts:1859
- MAX_SESSION_RETRIES = 1

The MCP tool first calls:
- ensureConnectedClient(client)

It then calls:
- callMCPToolWithUrlElicitationRetry(...)

A session-level retry occurs only when:
- the error is McpSessionExpiredError
- attempt < MAX_SESSION_RETRIES

This means:
- one initial session attempt
- at most one session-recovery retry

The maximum session-level attempt count is therefore 2.

4. URL elicitation retry
------------------------

src/services/mcp/client.ts:2850
- MAX_URL_ELICITATION_RETRIES = 3

The wrapper initially calls:
- callToolFn(...)

It retries only when the error is:
- ErrorCode.UrlElicitationRequired

This retry is not a normal network retry.

It occurs when:
- the MCP tool requires the user to open or complete a URL interaction
- hooks or the user process the elicitation
- the same MCP tool is then called again

Possible handling paths include:
- automated elicitation hook
- structured I/O handler
- REPL elicitation queue
- user acceptance
- user decline
- user cancellation

If the interaction is accepted, the loop retries the tool call.

If it is declined or cancelled, the wrapper returns explanatory content without retrying.

The maximum URL-elicitation-level attempt count is:
- one initial call
- up to three retries
- maximum 4 attempts

7. Timeout handling
-------------------

The timeout value is obtained through:
- getMcpToolTimeoutMs()

The SDK call receives:
- timeout: timeoutMs

The code also creates its own timeout Promise and uses:

Promise.race([
  client.callTool(...),
  timeoutPromise
])

This provides an additional timeout layer when the SDK timeout does not complete correctly.

The timeout timer is cleared in finally.

Long-running MCP calls also produce progress logging every:
- 30000 ms
- 30 seconds

9. Important static-analysis implications
-----------------------------------------

A scanner should not only report:
- client.callTool(...)

The upper layers provide important information about:
- model-facing tool identity
- MCP server name
- tool name
- input schema
- arguments
- metadata
- session retry
- URL elicitation retry
- timeout
- AbortSignal
- progress handling

The MCP path also demonstrates:
- dynamically created tool objects
- closure-captured server and tool metadata
- wrapper functions
- dependency injection
- multiple nested retry mechanisms

The analyser may need linked findings or a call-chain representation.

10. Runtime information still required

- actual number of MCP calls
